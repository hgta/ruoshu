# 01 · 技术选型全面对比

> 前提：上云部署（腾讯云/阿里云），技术栈不限于 PHP + MySQL。
> 评估维度：开发效率、并发能力、实时通信、生态、人力可得性、与"版权保护"特性的匹配度。

---

## 一、后端语言全面对比

### 1.1 总览矩阵

| 维度 | PHP (Laravel/Hyperf) | Go (Gin/Kratos) | Java (Spring Boot) | Node.js (NestJS) | Python (FastAPI) |
|------|---------------------|-----------------|--------------------|-------------------|------------------|
| 开发效率 | ⭐⭐⭐⭐ 快 | ⭐⭐⭐ 中 | ⭐⭐ 慢（样板多） | ⭐⭐⭐⭐ 快 | ⭐⭐⭐⭐ 快 |
| 并发能力 | FPM 弱 / Swoole 强 | ⭐⭐⭐⭐⭐ 原生强 | ⭐⭐⭐⭐ 线程模型 | ⭐⭐⭐⭐ 事件循环 | ⭐⭐ 异步弱 |
| WebSocket/实时 | FPM ❌ / Swoole ✅ | ✅ 原生 | ✅（偏重） | ✅ 最顺手 | ⭐⭐ 一般 |
| 生态成熟度 | CMS 类最丰富 | 云原生丰富 | 企业级最全 | 全栈 JS | AI/ML 独一档 |
| 国内人才密度 | 高 | 高（新项目主流） | 最高 | 中 | 中 |
| 内容平台先例 | 晋江(早期)、WordPress 系 | 番茄系外围服务 | 起点/阅文核心 | 中小型平台 | 几乎不做主站 |
| ML/AI 集成 | 弱 | 弱 | 中 | 弱 | ⭐⭐⭐⭐⭐ |
| 单机部署复杂度 | 低 | 极低（单二进制） | 高（JVM） | 低 | 低 |

### 1.2 关键洞察

1. **国内网文大厂主站清一色 Java**（阅文），新锐服务用 Go（字节系番茄的推荐/中间件），
   PHP 只存在于早期或外围系统 —— 但这不意味着小团队该学阅文。
2. **阅文用 Java 微服务是因为千人团队**。10 人以下团队用 Java 微服务是自虐，
   单体 + 少量长连接服务才是正解。
3. **Python 不适合做主站**（性能天花板低），但 AI 检测、文本水印、语义分析必须用 Python —— 它是"边车"而非"引擎"。
4. **Node.js 的优势是全栈同构**（SSR + 实时），但内容平台的核心负载是"读多写少 +
   大文本渲染"，Node 的单线程模型在 CPU 密集的文本处理（水印、哈希、分词）上反而是短板。

### 1.3 候选架构方案

#### 方案 A：纯 PHP 单体（Laravel + Livewire/Inertia）—— 最快上线

```
┌────────────────────────────────────────────┐
│  Nginx → Laravel (PHP-FPM)                 │
│  ├─ Web / API / 后台                        │
│  ├─ MySQL 8 + Redis + Meilisearch           │
│  └─ 定时任务：存证批量上链、水印生成           │
└────────────────────────────────────────────┘
实时能力：❌ 段评/弹幕降级为轮询（5s 延迟）
上手成本：最低。1-2 人 2-3 个月出 MVP。
```

#### 方案 B：PHP 主站 + Go 实时边车 —— 平衡之选（推荐）

```
┌───────────────────────┐   ┌─────────────────────┐
│ Laravel (PHP-FPM)    │   │ Go 服务 (长驻进程)    │
│ · 作品/章节/用户/支付  │◄──┤ · WebSocket 网关     │
│ · 后台管理/上链任务    │Redis│ · 段评/弹幕实时推送    │
│ · Web SSR            │ Pub/Sub│ · 在线状态/通知     │
└───────────────────────┘   └─────────────────────┘
          ▲                           ▲
          └──────────┬────────────────┘
                     │
        ┌────────────────────────┐
        │ Python FastAPI (边车)   │  · 文本盲水印生成/提取
        │ 仅内网调用，无公网暴露    │  · AIGC 检测对接
        │                        │  · 同义词替换消歧
        └────────────────────────┘
```
- PHP 做 80% 的业务（它最擅长的 CRUD + 模板渲染），Go 做 20% 长连接，Python 做 AI 特性。
- 三种语言通过 HTTP/gRPC + Redis 通信，边界清晰，各自独立部署独立扩容。
- 代价：三种技术栈的运维/人力成本。

#### 方案 C：Hyperf 一体化（Swoole 协程）—— 纯 PHP 阵营的现代答案

```
Hyperf 常驻协程进程
├─ HTTP Server（协程处理，性能≈Go 的 60-70%）
├─ WebSocket Server（同进程，共享连接管理）
├─ 协程定时任务（上链、水印、爬虫监测）
└─ 仍用 MySQL/Redis/Meilisearch
```
- 一个框架同时解决页面 + 实时，团队只需懂 PHP。
- 风险：Swoole 需编译扩展（云服务器可装，无碍），协程调试门槛高于 FPM，
  生态组件数量不及 Laravel（但 Hyperf 3.x 已覆盖主流场景）。

#### 方案 D：Go 全家桶 —— 性能上限最高

- Kratos / go-zero 微服务框架，单二进制部署，资源占用极低。
- 适合：预期 DAU 50 万+ 、团队本来就熟 Go。
- 代价：内容平台常见轮子（富文本管道、后台 CRUD 生成器、支付 SDK）都要自己攒，
  **开发周期比 Laravel 长 50%+**。

### 1.4 结论与推荐

```
┌─────────────────────────────────────────────────────┐
│ 团队规模          1-2 人        3-5 人        10 人+  │
│ 推荐方案          C 或 A        B（推荐）       B/D    │
│                                                     │
│ 原则：先单体后拆分；先 FPM 后长连接；先 MySQL 后扩展    │
└─────────────────────────────────────────────────────┘
```

**首选：方案 B**。理由：
1. Laravel 的开发效率保证 2-3 个月上线，抢占叙事窗口（"作者友好"这个定位很容被抄）
2. 段评/弹幕是这个平台"独特性"的一部分，实时能力不能阉割
3. 盲水印/AIGC 检测是核心差异化，Python 生态不可替代
4. 若团队只有 PHP 人力 → 降级到方案 C，功能不损失，只是性能余量小

## 二、数据层选型

### 2.1 MySQL 表设计要点（百万字长文场景）

```
books (作品)            chapters (章节元数据，热数据)
 ├─ id, title, author_id ├─ id, book_id, vol_no, chap_no
 ├─ status, word_count   ├─ title, word_count, is_vip
 └─ cover, tags          └─ published_at, hash, tx_id(链)
        │
        └──▶ chapter_contents (章节正文，冷数据，独立大表)
              ├─ chapter_id (PK)
              ├─ content MEDIUMTEXT   -- 单章上限 16MB，远超需求
              └─ (垂直拆分：大字段不进热查询)
```

- **垂直拆分是关键**：章节列表页只查元数据表（每行 <200B），正文单独一表，缓冲池不被大文本污染。
- 预估容量：10 万本书 × 平均 50 万字 × 3 字节(UTF-8) ≈ 150GB，单实例 MySQL 完全可扛，
  无需提前分库分表。**到 500GB 再谈 TiDB**。
- 归档策略：完结超 1 年的书正文可转冷存储（OSS 归档），读取时回源。

### 2.2 检索方案

| 方案 | 中文分词 | 资源占用 | 运维 | 适用 |
|------|---------|---------|------|------|
| MySQL FULLTEXT | 弱 | 低 | 零 | 不推荐做主检索 |
| **Meilisearch** | 内置，开箱即用 | 极低(单二进制) | 极简 | **文档<500万 首选** |
| Elasticsearch + IK | 强，可定制 | 高(JVM) | 重 | 复杂聚合/千万级文档 |
| Algolia(SaaS) | 好 | 零 | 零 | 贵，数据出境，不推荐 |

结论：**Meilisearch 起步**（书名/作者/标签/章节标题检索 + 容错纠错），等需要"全文内容搜索"
（用户搜某句话出处）时再上 ES + IK。

### 2.3 缓存与队列

- Redis：热章节正文缓存（命中率目标 >95%）、排行榜 ZSET、会话、限流计数
- 队列：Laravel Horizon (Redis 队列) 起步即可 —— 上链、水印、推送、邮件全是异步任务；
  日志量 >10 万条/天时换 RabbitMQ/Kafka（这个量级 99% 到不了）

## 三、云上部署架构（起步 → 中期）

### 3.1 起步期（DAU < 1 万，月预算 ~2000 元）

```
                        ┌─────────────┐
   用户 ──▶ CDN ───────▶│ SLB(负载)   │
        (静态/封面OSS)   └──────┬──────┘
                             ┌─┴──────────────┐
                             ▼                 ▼
                    ┌──────────────┐   ┌──────────────┐
                    │ CVM 2C4G     │   │ CVM 2C4G     │
                    │ Nginx+PHP    │   │ MySQL 8      │
                    │ Go 实时服务   │   │ (云数据库更稳)│
                    │ Redis        │   └──────────────┘
                    └──────────────┘
                    + OSS(封面/静态) + Meilisearch 跑在应用机上
```
- 用云数据库 MySQL（自动备份、只读实例可扩展），自建 MySQL 省钱但运维不值。
- 水印 Python 服务：Serverless 函数（SCF/FC）按量调用，闲时零成本。

### 3.2 中期（DAU 5-10 万）

- 应用层横向扩容（4-6 台 CVM）+ 独立 Redis 集群 + ES/Meili 独立实例
- Go 实时服务独立部署并扩容（连接数大头）
- WAF + 防爬（字体混淆在应用层做，见文档 02）

### 3.3 安全基线

- WAF（云厂商基础版即可，主要挡扫描器和脚本小子）
- 章节接口按用户级限流（如 30 章节/分钟），超限触发验证码
- 全站 HTTPS + HSTS；管理后台独立域名 + IP 白名单

## 四、分阶段演进路线

```
阶段 0 (M1-M2)  MVP 上线
  Laravel 单体：作品/章节/阅读/注册/后台
  至信链确权 API 接入（发布即存证）
  基础防盗：接口限流 + 禁右键/禁选择(前端) + 水印(可见的用户ID浮层)
                │
阶段 1 (M3-M5)  差异化特性
  Go WebSocket 服务：段评/弹幕/通知
  Python 边车：零宽+同义词盲水印、AIGC 检测接入
  Meilisearch 站内检索；作者一键导出(EPUB/MD/JSON)
  透明分账看板
                │
阶段 2 (M6-M12) 生态与反爬升级
  字体混淆渲染管线（自定义 woff 动态映射）
  盗版监测爬虫 + 哈希比对 + 一键取证（TSA）
  ActivityPub/RSS 联邦输出
  阅读端沉浸模式 + 段评氛围运营
                │
阶段 3 (12M+)   规模化
  按需拆分微服务（先拆：阅读服务、支付服务）
  ES 全文检索；多可用区；冷热数据分层
```
