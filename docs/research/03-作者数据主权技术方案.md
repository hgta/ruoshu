# 03 · 作者数据主权技术方案（深度版）

> 目标：把"作品归作者"从一句口号变成**可验证的产品能力**。
> 国内平台的本质问题是：作者离开平台 = 失去作品、失去读者、失去收益记录。
> 本方案让"离开"变得没有痛苦，反而以此赢得信任 —— 这是最高级的留人策略。

---

## 一、"数据主权"的四个组成部分

```
┌─────────────────────────────────────────────────────┐
│                     作者数据主权                       │
├──────────────┬──────────────┬─────────────┬──────────┤
│ ① 内容所有权  │ ② 数据可携带  │ ③ 分发自主权  │ ④ 收益透明 │
│ 作品归作者    │ 随时可带走    │ 不被平台绑架  │ 每分钱可查 │
│ (协议层)      │ (导出/标准格式)│ (RSS/联邦)   │ (分账引擎) │
└──────────────┴──────────────┴─────────────┴──────────┘
```

## 二、① 内容所有权：协议与授权体系设计

### 2.1 平台授权模型（与主流平台的根本区别）

| 条款 | 起点/晋江模式 | 番茄模式 | **本平台模式** |
|------|--------------|---------|---------------|
| 版权归属 | 平台买断或深度代理 | 平台长期授权 | **完全归作者** |
| 独家性 | 强制独家 | 事实独家 | **默认非独家**，独家为可选增值服务 |
| 授权范围 | 全版权(影视/游戏/出版) | 全版权 | **平台仅获得"信息网络传播权"的普通许可** |
| 作者违约金 | 高额违约金 | 高额违约金 | 无违约金，随时可下架停更 |
| 下架权 | 无（作品被平台锁死） | 无 | **作者随时下架，平台仅保留存证记录** |

### 2.2 CC 协议选择器（作者自选授权强度）

平台内置授权选择器，作品发布时必选：

```
推荐默认：CC BY-NC-ND 4.0
（署名-非商业性使用-禁止演绎）
  → 读者可自由转载传播（扩大影响力），但不得商用不得改写

可选项：
  ├─ CC BY-NC 4.0     允许同人二创（吸引二创生态）
  ├─ CC BY-ND 4.0     允许商用转载（作者自主开放）
  ├─ 全保留版权        传统模式，转载需逐次授权
  └─ 公有领域(CC0)     完全开放（极少用，但尊重作者选择）
```

**为什么 CC 选择器是差异化**：
1. CC 中国大陆版(3.0) 有官方移植文本，著作权法框架内有效
2. 把"别人转发我的书到底是侵权还是帮宣传"这个模糊地带**显式化**，作者省心
3. CC 协议自带标准化机器可读元数据（RDFa/微数据），未来可被搜索引擎/学术工具识别

### 2.3 协议的技术落点

- 注册/发布流程中**逐项明示**授权条款（不是藏在用户协议第 38 条）
- 每个作品页脚展示授权徽章（CC 图标 + 链接到协议全文）
- 授权选择的变更记录**哈希上链**（作者"何时选择了什么授权"不可篡改，防争议）
- 平台与作者之间的电子合同本身也走 TSA 时间戳签署

## 三、② 数据可携带性：一键导出体系

### 3.1 导出范围与格式

```
┌────────────────────────────────────────────────────┐
│ 作者中心 → 「我的数据」→ 一键导出                      │
├────────────────────────────────────────────────────┤
│ 内容数据                                              │
│  ├─ 正文：Markdown（保段落）/ EPUB3（保目录与元数据）   │
│  │         / TXT（保纯文本）/ JSON（保全量结构）         │
│  ├─ 版本历史：各章修订版本（JSON）                      │
│  └─ 创作过程数据：草稿、存证记录、修订时间线             │
│ 社交数据（UGC，导出时向作者声明归属与隐私处理）           │
│  ├─ 书评/段评（匿名化处理读者 PII 后提供）               │
│  └─ 读者互动统计（非个人级聚合数据）                     │
│ 收益数据                                              │
│  ├─ 分账流水全量（CSV + JSON，含链上存证引用）           │
│  └─ 汇总报表                                          │
│ 元数据                                                │
│  └─ tags、授权协议选择、封面源文件、ISBN(若有)           │
└────────────────────────────────────────────────────┘
打包：ZIP 异步生成（大书可能几百 MB）→ OSS 临时签名 URL（72h 过期）
```

### 3.2 技术要点

- 导出任务走队列，分片流式生成，不占 Web 进程
- EPUB 生成：PHP 生态较弱，由 Python 边车承担（ebooklib）
- **导出内容含存证哈希头**（JSON 内嵌 merkle root）：作者拿到的版本与其链上确权版本一致
  —— 作者可以拿这份文件在任何地方证明"这就是我当时发布的版本"
- 导出不限次数、不收费、不审核 —— 这是信任的底线（一次审核就毁掉全部叙事）

### 3.3 数据可携带性的"反向"价值

导出能力同时服务于**冷启动**：提供通用格式导入器（TXT/Markdown 智能分章），
配合"搬家即送流量包"运营策略。数据可携带是双向的 —— 作者可以从别处搬进来。

## 四、③ 分发自主权：不绑架作者的分发渠道

### 4.1 RSS/Feed 输出（一期即可做，成本极低）

```
每个作品自动生成：
  ├─ /feed/book/{book_id}.xml      章节更新 RSS
  ├─ /author/{id}.atom             作者主页 Atom
  └─ (可选) JSON Feed 1.1           现代阅读器兼容
```
- RSS 只含章节标题 + 摘要（前 200 字）+ 链接，引流回平台 —— **不损害付费内容**
- 读者可用任何 RSS 阅读器"追更"，作者不依赖平台 App 也能触达读者

### 4.2 ActivityPub 联邦出口（三期，战略储备）

```
┌────────────┐    ActivityPub     ┌──────────────────┐
│ 若书平台     │ ────────────────▶ │ Fediverse         │
│ (作为实例)   │   Note/Object      │ Mastodon/阅读客户端│
└────────────┘   章节发布广播        └──────────────────┘
```
- 实现路径：基于 Fedify(Node) 等库实现 Actor + Outbox，只做"发布广播"，
  不做跨站社交（工作量可控在 2-3 周）
- 价值：作者的粉丝在 Mastodon 能直接收到更新通知；平台给出"即使你不用我，
  也能用我的更新管道"的承诺 —— 反而增强信任
- 风险：国内访问 Fediverse 有障碍 → 定位为"面向海外读者的出口"，不影响主流程

### 4.3 通知渠道中立化

更新通知支持：站内信 / RSS / 邮件 / Webhook（作者可接自己的机器人）。
作者永远有办法触达自己的读者，即便离开平台（导出订阅者邮箱需读者逐个授权）。

## 五、④ 收益透明：分账引擎与"可审计的账本"

### 5.1 透明抽成模型（对标海外）

```
收入类型               平台抽成     说明
─────────────────────────────────────────────────
打赏                    5%         纯通道成本
章节付费                15%        含支付通道+存证成本
订阅制                  10%        规模化后可降
版权代理(影视/出版撮合)   10% 或协商  平台只做撮合，不强制代理
─────────────────────────────────────────────────
对照：起点 ~50% / Patreon 5-12% / Substack 10%
定价逻辑：覆盖成本(支付通道约1-3% + 存证 + 带宽) + 小比例利润
叙事价值 > 利润价值
```

### 5.2 可审计分账账本（核心创新点）

```
┌──────────────────────────────────────────────────────┐
│ 每笔收入产生时：                                        │
│  (order_id, book_id, chapter_id, user_id,             │
│   amount, platform_fee, author_income, timestamp)     │
│      │                                               │
│      ├─ 写入 MySQL 流水表（明细逐笔可查）                 │
│      ├─ 每小时聚合 → Merkle root 上链（见文档04）         │
│      └─ 作者端展示：每笔分成的"链上校验"按钮               │
│          → 用平台公开的验证接口核对哈希                   │
└──────────────────────────────────────────────────────┘
```

- 作者看板：实时收入、按书/按章分解、抽成明细逐笔可查
- 每月生成"对账单"（含链上 root 引用）+ TSA 时间戳 → 争议时有据可查
- **平台无法篡改历史账目**（本地改了哈希对不上链）→ "透明"的技术证明，不是口号

### 5.3 结算合规提示

- 个人作者代扣代缴个税，或引导注册个体户（平台作为支付方有合规义务）
- 支付通道：微信/支付宝官方商户 + 官方分账接口（微信支付分账/支付宝分账），
  **避免二清风险** —— 这是平台型收款的合规红线

## 六、数据模型（概念级）

```
author_grants (作者授权选择记录)
├─ author_id, book_id, license_type (CC BY-NC-ND / all_rights / ...)
├─ granted_at, tx_id (上链), doc_hash (协议文本哈希)

exports (导出任务)
├─ author_id, scope(内容/收益/全量), status
├─ oss_url, expires_at, file_hash

ledger_entries (分账流水)
├─ order_id, book_id, chapter_id
├─ gross, platform_fee_rate, platform_fee, net
├─ batch_id → merkle_root (链), created_at
```

## 七、实施分期

| 阶段 | 内容 | 工作量 | 优先级 |
|------|------|--------|--------|
| 一期 | 授权选择器（4 种 CC + 全保留）+ 协议明示 + TXT/MD 导出 + RSS | 2 周 | ★★★★★ |
| 一期 | 透明分账看板（逐笔明细，暂不上链） | 1 周 | ★★★★★ |
| 二期 | EPUB/JSON 全量导出 + 导入器(搬家工具) + 分账 Merkle 上链 | 3 周 | ★★★★ |
| 三期 | ActivityPub 出口 + Webhook 通知 + 授权变更上链存证 | 3 周 | ★★★ |

## 八、竞品参照与本方案的独特性

```
Substack：数据主权标杆（随时带走订阅者邮箱），但无版权技术保护
Ko-fi   ：抽成 0% 但无平台级确权/溯源能力
本平台  ：Substack 式的主权承诺 + 起点式的内容生态能力
        + 起点没有的版权保护技术栈（水印/指纹/链上确权/溯源取证）
        = 国内外均无完整对标的产品形态
```

**核心警示**：数据主权是"信任产品"，一次丑闻（如偷偷改协议、导出设障碍）就永久破产。
上线前必须把授权条款交法律顾问审过，宁可条款保守也不要有暗坑。
