# 08 · 数据库 ER 图与核心表设计

> 设计基线 · 2026-09-28
> MySQL 8 · InnoDB · utf8mb4。核心设计原则：热冷分离（正文垂直拆分）、
> 多态评论、唯一真源账本（ledger）、指纹与存证旁路化。

## 二、关键表结构（字段级）

### users / author_profiles / reader_profiles

```sql
users
  id, phone, wechat_openid (唯一), email
  nickname, avatar_url
  role_flags (bitmap: reader|author|admin)
  status (active/banned)
  created_at, last_login_at

author_profiles                -- 实名信息（存证主体资格）
  user_id (PK,FK)
  pen_name, real_name, id_number_hash  -- 实名信息只存哈希+脱敏
  contract_status (none/signed)
  bank_account_encrypted, tax_info_encrypted
  total_earnings_cached          -- 累计收益缓存（真源在 ledger）
```

### books / chapters / chapter_contents / paragraphs

```sql
books
  id, author_id, title, subtitle
  category (enum: 古风言情/现言都市/玄幻仙侠/奇幻冒险/科幻悬疑/轻小说)
  intro_text, cover_url
  status (draft/serializing/completed/shelved)
  word_count_cached, chapter_count_cached
  license_type (CC_BY_NC_ND/CC_BY_NC/CC_BY_ND/ALL_RIGHTS/CC0)
  is_vip, monoprice_per_chapter (default 0.2)
  latest_chapter_id, finished_at
  created_at, updated_at

chapters                       -- 元数据表（热查询：目录页/更新列表）
  id, book_id, volume_no, chapter_no
  title, word_count
  is_vip, price_cents (单章定价，分)
  status (draft/scheduled/published/removed)
  published_at
  -- 注意：无 content 字段！
  tx_id (最新存证链上ID，FK→evidence_records)

chapter_contents               -- 正文表（冷，大字段独立）
  chapter_id (PK), content MEDIUMTEXT
  content_version              -- 与 chapters 最新版本对应
  updated_at

paragraphs                     -- 段落指纹（发布时生成，只读）
  id, chapter_id, para_no
  para_hash (SHA-256 of 规范化文本)
  merkle_path                  -- 可选：验证路径 JSON
  created_at
```

### 收入三源 + 唯一账本

```sql
donations                      -- 打赏（主变现）
  id, from_user_id, to_author_id, book_id, chapter_id (nullable)
  gift_id, amount_cents
  message, status (paid/refunded)
  paid_at

chapter_purchases              -- 章节单购
  id, user_id, chapter_id, price_cents
  status, paid_at
  UNIQUE(user_id, chapter_id)

subscriptions                   -- 订阅（月卡会员 / 单书订阅）
  id, user_id, target_type (monthly_member/single_book)
  target_id (book_id, nullable for 月卡)
  period_start, period_end
  price_cents, status (active/expired/cancelled)
  paid_at

ledger_entries                  -- ★ 唯一真源：所有金钱流动
  id, source_type (donation/purchase/subscription)
  source_id                    -- 对应上面三张表的 id
  order_no (对外流水号)
  book_id, chapter_id, author_id, user_id
  gross_cents, platform_fee_rate
  platform_fee_cents, author_net_cents
  batch_id (FK→merkle_batches)
  entry_hash                    -- 单条哈希（含前一条 hash：链式）
  created_at

merkle_batches                  -- 上链批次
  id, batch_type (ledger/evidence/audit)
  period_start, period_end
  merkle_root, tx_id (至信链返回)
  tsa_cert_id (若有 TSA 双存证)
  entry_count, status (pending/submitted/confirmed/failed)
```

### 水印与存证（旁路表）

```sql
watermark_seeds
  id, user_id, chapter_id (UNIQUE 联合)
  seed, payload, engine_version
  created_at

evidence_records               -- 存证记录
  id, target_type (chapter/contract/license/audit)
  target_id
  payload_hash (上链 JSON 的哈希)
  tx_id, chain (zhixin/ant/tsa)
  status (pending/submitted/confirmed)
  certified_at, created_at

watermark_audits               -- 溯源结果
  id, book_id, chapter_id
  evidence_url (盗版来源)
  matched_paragraph_count, similarity_score
  extracted_user_id, confidence
  chain_cert_id (FK→evidence_records, 取证包存证)
  status, created_at
```

### 社交

```sql
comments                       -- 多态：段评/章评/书评
  id, user_id
  target_type (paragraph/chapter/book)
  target_id
  parent_id (楼中楼), content
  like_count_cached, status (visible/hidden/deleted)
  created_at

danmu                          -- 弹幕（实时流，定期归档）
  id, chapter_id, paragraph_no
  user_id, content, style (float/top)
  created_at

book_tags                      -- N:M
  book_id, tag_id (联合 PK)

gifts                          -- 礼物定义
  id, name, icon, price_cents, animation_type, sort
```

## 三、设计要点说明

```
1. 垂直拆分章节正文
   chapters（元数据，热）与 chapter_contents（正文，冷）分离。
   目录页/更新列表只查元数据表（每行 <200B），缓冲池不被大文本污染。

2. 多态评论
   comments 用 (target_type, target_id) 指向段/章/书，避免三张表 UNION。
   段评高频读写：target_type+target_id 建复合索引。

3. 段落指纹发布后只读
   paragraphs 在发布时生成快照；正文修订产生新指纹批次（版本化），
   历史比对用旧批次 —— 保证"当时发布的版本"永远可验证。

4. ledger_entries 是唯一真源
   donations/purchases/subscriptions 落库时同事务写入 ledger；
   作者端展示、对账单、上链全部从 ledger 出，不从源表算账。
   entry_hash 链式（含前一条哈希），Merkle 批次上链。

5. 弹幕与段评分离
   danmu 是实时流（可过期、可归档、可丢弃），comments 是沉淀资产。
   数据结构、缓存策略、清理策略完全不同。

6. 导出与溯源是旁路
   exports/watermark_audits 不参与核心读写路径，量大时独立归档即可。

7. 金额一律用"分"(cents)
   避免浮点误差，平台费率存字段而非代码，方便调整留痕。

8. 全库 utf8mb4
   从 M1 起就为多语言铺路（海外预留，见研究文档 00 决策记录）。
```

## 四、预估容量与索引策略（基线规模：500 部 / DAU 3000）

```
表                起步量级        一年后量级        备注
books             500            5,000            无压力
chapters          30,000         500,000          联合索引(book_id, chapter_no)
chapter_contents  30,000         500,000          ≈1.5GB/年，单实例可扛
paragraphs        3,000,000      40,000,000       仅插入，冷归档
comments          1,000,000      20,000,000       复合索引(target_type,target_id,id)
danmu             5,000,000      100,000,000      Redis 热存 + 定期归档 MySQL/OSS
ledger_entries    500,000        10,000,000       链式哈希+批次索引

结论：基线规模下单 MySQL 实例（4C8G）+ Redis 完全够用；
paragraphs/danmu 到千万级再考虑分区或归档，500GB 前不谈分库分表。
```
