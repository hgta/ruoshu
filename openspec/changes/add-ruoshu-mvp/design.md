# Design: add-ruoshu-mvp

## Context

全新项目（greenfield）。前期已完成完整研究（`ruoshu/docs/research/`）与设计基线
（`ruoshu/docs/design/`），8 项关键决策已锁定：

1. 技术栈 = 方案 B（Laravel 主站 + Go 实时 + Python 边车）
2. 存证 = 至信链按量 1 元/条 + TSA 取证包
3. 用户群 = 女频 + 轻小说（轻小说独立成类）
4. 商业 = 打赏为主 + 章节单购 + 月卡订阅
5. 分类 = 6 大类 + 标签云
6. 不做独家签约（替代钩子：透明分账/版权保护/IP 撮合）
7. 规模基线 = 500 部 / 日更 150 章 / DAU 3000 / 月成本 6000-8000 元
8. 海外不出海但铺路（utf8mb4 + i18n key + RSS 预留）

本设计文档只记录 MVP 实现层面的关键决策，深度技术细节引用研究文档，不重复。

## Goals / Non-Goals

**Goals:**
- 3 个月内上线可运营的 MVP：读者可看可打赏、作者可发书可收钱可存证可溯源
- 三个差异化能力真实可用：①发布即存证（至信链）②付费章节 per-user 盲水印（W1）
  ③透明分账 ledger（作者逐笔可查）
- 作者主权的最低可信集：CC 授权选择器 + Markdown/TXT 导出 + RSS
- 体验红线：注册回到阅读 ≤15s、打赏反馈 ≤3s、存证异步无感、段评即发即上屏

**Non-Goals（本 change 明确不做）:**
- 同义词水印 W2 / 渲染层字体指纹 W4 / 字体混淆反爬（放后续 change）
- ActivityPub 联邦（RSS 已预留出口）
- 推荐算法（用编辑人工 + 标签匹配）
- 独家签约体系、海外支付、EPUB 导出（Markdown/TXT 够 MVP）
- 分账账本逐小时上链（MVP 只做 ledger 链式哈希 + 月度 TSA 对账单，批次上链放二期）
- 手机 App（移动端 H5 响应式优先）

## Decisions

### D1. Monorepo 三服务布局

```
ruoshu/
├─ apps/web/          Laravel 11 主站（全部业务页面 + API + 队列）
├─ apps/realtime/     Go 1.22+ 服务（WebSocket：段评/弹幕/通知广播）
├─ services/ai-python/ FastAPI 边车（仅内网：水印种子生成、指纹规范化）
├─ infra/             docker-compose（开发）/ 部署脚本 / nginx
└─ docs/              （已有 research + design 文档）
```

**为什么 monorepo**：3 人以下团队，跨服务改动（如段落锚点格式）需要原子提交；
拆 repo 的协调成本对小团队是纯损耗。
**备选**：三 repo —— 被否，变更同步靠人肉记性不可靠。

### D2. 服务间通信：只走 Redis + HTTP，不引 gRPC/消息队列

- Laravel → Go：Redis Pub/Sub（频道 `book:{id}:ch:{id}` 广播弹幕/段评）
- Laravel → Python：内网 HTTP（同步，超时 3s；水印种子生成是低频操作）
- 队列：Laravel Horizon（Redis 队列）承担存证上链、指纹生成、导出打包
**为什么**：基线规模（DAU 3000）下没有消息量可言；gRPC 会给 3 语言项目增加
protobuf 工具链负担。**升级路径**：Redis Pub/Sub 不满足时换 NATS，接口已按
"发布订阅"语义抽象。

### D3. 数据库：单 MySQL，正文垂直拆分，不用分库分表

沿用设计基线 08：`chapters`（热元数据）/ `chapter_contents`（冷正文 MEDIUMTEXT）
分离；`paragraphs` 段落指纹只读快照；`ledger_entries` 唯一真源 + 链式哈希。
金额一律 cents。utf8mb4。
**为什么**：基线规模 1.5GB/年正文增长，单实例（4C8G 云数据库）三年内不触顶。
500GB 前谈分库分表都是过度设计。

### D4. 存证：至信链驱动抽象 + 本地哈希先行

- 发布流程：正文落库 → 规范化/分段/哈希（Python 边车）→ Merkle root +
  元数据 JSON → 队列提交至信链 → tx_id 回写 `evidence_records`
- **哈希与载荷在提交前已持久化本地**（OSS + MySQL），链服务故障不丢证据
- 存证服务以 driver 接口抽象（`ZhixinChainDriver`），换链=换驱动（研究文档 04 对冲设计）
- 免费书每日打包存证（1 条/天），付费书逐章存证（1 元/章）
- MVP 只接至信链；TSA 时间戳仅在"月度对账单"与"取证包"两个场景调用（低频）

### D5. 盲水印 MVP = 仅 W1 零宽字符，且只对付费章节启用

- payload = user_id + ECC 校验位，编码为零宽序列，按标点位置嵌入
- 嵌入在 Laravel 渲染层完成（纯字符串处理，无需 Python）；
  Python 边车只负责发布时的"嵌入点规划"（选哪些标点、生成方案）与溯源时的提取
- 水印方案 per (user, chapter) 确定性（同用户重复读结果一致，防自我比对破解）
- 溯源工作台：作者粘贴盗版文本 → 指纹比对（命中章节）→ 零宽提取 → 定位账号
  → 生成取证包（链证书 + 哈希清单 + 比对报告 PDF）
**为什么不做 W2**：等价对库需 4-6 周词库建设，且改写文本有读者感知风险，
MVP 用 W1 先跑通"可溯源"叙事，W2/W4 放独立后续 change。

### D6. 付费与分账：官方分账接口，杜绝二清

- 微信支付 + 支付宝官方分账 API；平台商户接收 → 分账给作者（需作者签约个体户/
  委托代扣协议，法务模板在 M1 前定稿）
- `ledger_entries` 与收入源表同事务写入，entry_hash 链式（含前一条哈希）
- 作者端逐笔可见：金额、抽成、净得，实时看板
- 月度对账单 PDF + TSA 时间戳（MVP 的账本"防篡改"由链式哈希 + 月度 TSA 承担；
  逐批上链是二期）
**抽成**：打赏 5% / 章节付费 15% / 月卡 10%（协议已锁定的对外承诺值）

### D7. 实时服务：Go 单二进制，广播风暴之外的功能都不做

Go 服务只做三件事：连接管理（WebSocket）、订阅 Redis 频道并转发、
断线降级标记。鉴权在握手时用 Laravel 签发的 JWT（短时效，复用主站 user 表）。
**前端**：WebSocket 不可用时自动降级 5s 轮询（体验红线允许）。

### D8. 搜索：Meilisearch 单实例，只索引元数据

索引 books（标题/作者/标签/简介摘要）与 chapters（章节标题），不索引正文。
正文全文检索（搜某句话）明确是二期。
**为什么**：Meilisearch 单二进制 + 自带中文分词，运维成本接近零；
基线 500 部书的数据量连 ES 的启动内存都不值得。

### D9. 后台：Filament（Laravel 生态）而非独立前端

管理后台用 Filament 5 直接生成（用户/审核/举报/财务四模块），
独立子域 + IP 白名单 + TOTP 2FA。**为什么**：管理后台是内部工具，
用 Vue/React 单独建前端会翻倍工作量；Filament 的 audit 扩展直接满足留痕要求。

### D10. 部署：双机起步，Docker Compose，无 K8s

```
节点1（应用）：Nginx + Laravel(FPM) + Go 服务 + Meilisearch + Horizon 队列
节点2（数据）：云数据库 MySQL（购买）+ Redis（购买）
OSS + CDN：封面/静态/导出包
```
CI：GitHub Actions（PHP/Go/Python lint+test 三管线）。
**为什么不上 K8s**：两个进程的编排用 systemd/supervisor 足够，
K8s 的运维复杂度对 3 人团队是负资产。

## Risks / Trade-offs

- [至信链 API 变更/停服] → driver 抽象 + 本地哈希先行，任何时刻可换链补存；
  补存的哈希与时间以本地为准，链仅背书
- [零宽水印被清洗] → MVP 已知局限；W1 的目标是"溯源懒惰盗版商 + 威慑"，
  W2/W4 在后续 change 补齐；溯源置信度不足时输出"人工比对报告"而非误封
- [作者分账合规（二清红线）] → 必须走官方分账接口；作者协议 + 个体户引导流程
  未过法务前，打赏功能不开放（功能开关控制上线顺序）
- [3 语言小团队的认知负担] → 服务边界硬约束：Go 只碰实时、Python 只碰文本处理；
  跨服务接口改动必须 atomic commit；每个服务 README 说明"我不管什么"
- [正文 MEDIUMTEXT 16MB 上限] → 单章 16MB ≈ 500 万字，无现实风险；
  编辑器端限制单章 ≤10 万字（行业惯例 5 千-1 万）
- [女频内容审核风险] → 敏感词库 + 发布前预检 + 人工抽审 SOP 上线前就绪；
  存证平台的内容责任更重，审核不到位就不开放注册
- [Meilisearch 中文分词精度] → MVP 只做标题级搜索，精度够用；
  真实用户反馈驱动后续决策（ES+IK 备选路径已写在研究文档 01）

## Migration Plan

Greenfield，无存量迁移。部署顺序：
1. 基础设施（云资源 + CI + 环境骨架）先行
2. web 起步阶段可独立上线（realtime 未就绪时前端自动走轮询降级）
3. 支付/分账模块由功能开关控制，法务材料就绪后才开启
4. 回滚策略：单服务回滚（Laravel/Go 各自独立部署），数据库变更走
   迁移脚本且只加不删（回滚 = 代码回退，schema 向后兼容）
